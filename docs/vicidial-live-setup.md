# VICIdial live calling setup

For direct phone-extension diagnostics without a campaign call, use the separate [manual audio test guide](vicidial-manual-audio-test.md). Production call verification remains enabled.

Campaign management, migration, exact validation results and remaining limitations: [implementation handover](vicidial-campaign-implementation.md).

The implementation is ready for installation and a supervised dialer test. No real VICIdial server, carrier, audio route, credentials or recordings were available during implementation. Saving API credentials alone does not configure Asterisk media.

The supplied bridge supports campaign/script pools, AI-only recordings and human-answer-confirmed AI release. The dialer administrator must install the actual human-answer/customer-end hooks and configure transfer waiting music on the installed VICIdial/Asterisk system. These event mappings cannot be inferred from API credentials alone.

## Check Asterisk compatibility before installing the route

A reported deployment log identifies `13.38.3-vici`. Standard `AudioSocket()` was introduced in Asterisk 18.0.0; do not assume this Asterisk 13 build contains it. On the actual server, inspect `core show application AudioSocket` and `module show like audiosocket` first. A custom backport would need explicit verification. If absent, the engineer must design a supported compatible gateway/deployment path; the supplied AudioSocket dialplan cannot run unchanged on a stock Asterisk 13 server. See the [official application requirements](https://docs.asterisk.org/Asterisk_20_Documentation/API_Documentation/Dialplan_Applications/AudioSocket/).

An empty `SHAHVEX_AUDIO_UUID` means registration failed. The updated AGI emits a credential-free `VERBOSE` reason before returning an empty value. It distinguishes invalid caller-code, missing/unreadable JSON config, bridge connectivity, authentication, unprepared lines and capacity. Install the updated script at the exact path used by your dialplan (the reported server uses `/var/lib/asterisk/agi-bin/register-call.py`). Do not print the secret file to diagnose it.

A phone manually dialing the extension with CallerID name such as `ext 78601` is not an authorized VICIdial campaign call. Registration requires the original VICIdial caller-code and a prepared Remote Agent line. Do not fabricate caller-codes or bypass the website's Native call verification. A real answered campaign call remains required for the production flow.

## Install the supplied bridge

The bridge uses Node 20+ and Python 3, with no additional packages. Deploy one bridge process per connection; the connection can contain multiple AI lines. Set SHAHVEX_VICIDIAL_MAX_CALLS to the concurrency actually provisioned and load-tested on the dialer and AI server (the sample defaults to 10). Starting agents cannot reserve more remote lines than this configured bridge capacity.

1. Save the connection and agent routing in VoIP. Copy its connection UUID. Before creating the connection, set `SHAHVEX_VICIDIAL_BRIDGE_URL` and `SHAHVEX_VICIDIAL_BRIDGE_SECRET` in the website server environment. Use the same random secret of at least 32 characters on the bridge. Both VoIP portals show read-only bridge settings. Do not put secrets in dialplan arguments or URLs.
2. Copy `deployment/vicidial-bridge/server.cjs`, `ai-recording.cjs`, `register-call.py` and `handoff-event.py` into `/opt/shahvex-vicidial/`. Make both Python files executable. Copy `bridge.env.example` to `/etc/shahvex-vicidial.env`, fill in the site URL, connection UUID and shared secret, and restrict access to the service account.
3. Create `/etc/shahvex-vicidial.json`, readable only by root and the Asterisk service account, containing `{"controlUrl":"http://127.0.0.1:8790","secret":"THE_SAME_SECRET"}`. Install the supplied systemd unit after adjusting the service user and Node path to your host. Its state directory holds prepared line mappings and durable event retries.
4. Publish the bridge's HTTP control server on a dedicated HTTPS origin using your existing TLS reverse proxy. Preserve request paths and bodies. The server authenticates every operation with timestamped HMAC. Keep TCP 9019 private. If using private hosts from the website, add those exact hostnames to `SHAHVEX_VOIP_ALLOWED_HOSTS` on the website server; do not disable host validation.
5. Have the dialer administrator adapt `extensions-shahvex.conf.example` to the installed VICIdial dialplan and remote phones. The example is not a replacement for the site's existing dialplan. Each Remote Agent must dial its matching custom phone extension; do not route customer carrier calls directly into this context.
6. Add the human transfer hooks to the real human/customer bridge and customer termination handlers. Invoke `AGI(/opt/shahvex-vicidial/handoff-event.py,human-answered,ORIGINAL_VICIDIAL_CALLER_CODE,HUMAN_USER)` only after the customer and real human are actually bridged. Invoke `AGI(/opt/shahvex-vicidial/handoff-event.py,customer-ended,ORIGINAL_VICIDIAL_CALLER_CODE)` when that customer leaves. Replace the placeholder arguments with the installed system's actual variables and carry the original caller-code through the transfer. The hook posts a signed event to the local bridge; the website independently checks the human's live lead/status before completing the AI call. Configure the in-group's waiting music on VICIdial/Asterisk.
7. On the website, enable VICIdial live calling and enter remote users, human in-group and the optional recording base URL. In **VoIP > Assign agent route**, select the connection and agent, then enter the existing Remote Agent ID and four-character AudioSocket extension. The BPO portal lists its own agents and connections. A controller with VoIP permission can also select BPO workspaces in the controller portal. Confirm that recording is enabled on the campaign. Run **Test connection**, then **Test audio bridge**. The latter checks the bridge service and protocol; it does not certify a live carrier/audio/transfer route.
8. Create the AI profile separately. In VoIP, select a saved connection for a campaign, supply its script for automatic extraction, assign available agents, then start campaign intake. Each agent can belong to one campaign. The website enables its remote-agent line. VICIdial uses its existing campaign lists and dials; only an answered, API-verified customer call in that campaign receives the matching available AI agent. The website does not import, add or originate campaign numbers. **Start call** queues the agent; it does not create a fake live customer call.

## Shared tester instructions

Browser testing and VICIdial use `scriptTestConfig` in `lib/agent-script-details.ts`, the same `extractAgentScript`, `newTest` and `agent-test-speculative` turn handler. The instruction text remains in `lib/agent-test.ts`. Live calling does not append separate personal/campaign instruction overrides to the spoken prompt. Campaign transfer requirements and recording settings remain telephony metadata outside that prompt. The PC path uses the same `/tester/start` and tester turn endpoints. A regression test checks exact configuration and system-message equality for the same script/profile; it does not certify a real carrier call.

## Behavior and recovery

- Campaign numbers and lists remain entirely in VICIdial. The website never calls `add_lead` or requires a number sheet or list ID to start an AI line. BPO script uploads and VICIdial agent creation support a script without a customer sheet.
- Each AI agent is mapped to a configured campaign and a dedicated remote-agent line. Its assigned script is snapshotted for that call. A free eligible member of the same campaign/script pool receives the answered call; busy members are skipped even if the incoming transport line originally belonged to one of them. The callback verifies campaign, caller-code and lead ID against VICIdial and retrieves the customer number from native lead details. Stop the existing queue before changing a running agent's campaign/script.
- Agent availability is checked under a database row lock; a busy, unapproved, out-of-schedule or exhausted agent cannot receive another website call. Dedicated remote lines supply capacity to VICIdial; calls are not originated through Telnyx for a connection with live VICIdial enabled.
- Conversation setup uses the same extraction, `newTest`/PC tester session, turn handler and streamed speech path as testing. The shared time-permission and interruption filters remain in place. The master prompt additionally requires truthful AI identity, so the former human-identity claim was corrected in the shared prompt. Call sessions use separate owners and do not replace a browser test session.
- Actual user answers are stored with the transcript and source evidence. Unsupported extracted values are discarded. All collected fields remain in `agent_calls.collected_fields`; compact lead details are synchronized to VICIdial comments after turns and at the end. The default comments capacity is 255 characters until the engineer verifies another limit. Synchronization preserves operator comments and updates only the marked AI block; if the summary cannot fit, it uses a call reference. If even the reference cannot fit, synchronization fails and transfer stays blocked. Full fields and evidence stay on the website; retries are bounded and durable.
- Human transfer requires completed required pre-handoff tasks (or an explicit request to speak to a human), actual customer consent, synchronized comments and a ready agent in the configured human-only in-group. `ra_call_control` performs the transfer. A successful API response means **submitted**, not that the human has answered. A timed-out transfer is **UNCERTAIN** and is not retried automatically; reconcile it on the dialer first. With no human ready, the call stays with AI and a durable retry is retained. The AI remains busy while awaiting the human. A signed human-answer hook, verified against VICIdial live status for the same lead, requests AI media closure. Only after AI leg closure is also confirmed does the website complete the AI call and release its runtime; the human/customer call continues on VICIdial.
- The bridge records only the AI/customer audio leg as a private stereo WAV. It lets queued AI speech finish, closes this recording before requesting the human transfer, and never appends human audio. The website proxies that AI-only file with signed access through its authenticated recording pages. Native full recordings remain on VICIdial and are not used as a website fallback. Keep the bridge state directory on persistent storage and configure its backup/retention. Partial AI recordings can be finalized after a bridge restart.
- The bridge retries pending completion/comment/recording events from disk, including after restart. Previously active AI calls are reconciled against native agent status and closed rather than restarting their introduction. It checks queue schedules/allowances every 15 seconds. Keep the bridge and website reachable; the installed dialer must also enforce its own call-time and DNC rules independently.
- **Stop queue** disables the dedicated remote entry; an already connected call can finish. Live hangup uses VICIdial control. Hold/resume pauses AI media in the bridge. Campaign recording is managed on VICIdial rather than pretending the old Telnyx recording buttons control the remote-agent recorder.

## Supervised acceptance check before normal use

Use approved test numbers: two AI agents assigned to one campaign without website number sheets, one answered customer, one busy AI, one ready human, one unavailable human, a refused transfer, a duplicate/retried callback, an interrupted utterance, a bridge restart, and a completed call. Confirm that no numbers are uploaded by the website, correct script/voice, customer-only audio input, paced two-way playback, full native recording including human handoff, separate AI-only website playback, verified human-answer release without hanging up the human/customer, exact collected fields in the website, compact comments in VICIdial, and confirmed dialer transfer/disposition. Verify the campaign can dial with these remote entries before increasing concurrency.

Implementation follows the official [VICIdial Non-Agent API](https://www.vicidial.org/docs/NON-AGENT_API.txt), [Agent API](https://www.vicidial.org/docs/AGENT_API.txt) and [Asterisk AudioSocket protocol](https://docs.asterisk.org/Configuration/Channel-Drivers/AudioSocket/). Check those against the installed build during setup.
