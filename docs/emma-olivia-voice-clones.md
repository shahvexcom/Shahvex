## Generation and preservation

Both revised previews were actually generated by an isolated CPU instance of the
existing Fun-CosyVoice3-0.5B model, then checked for non-silent mono 24 kHz PCM and
transcribed locally. Both previews recover the configured name and requested text,
including mm-hmm. No new inference settings were applied to the production model.
These checks establish generated speech and content; speaker resemblance and tone
still need listening review and are not guaranteed by transcription.

The corrected references and metadata were copied only into the restored backend's
Emma and Olivia folders. Existing files for those two voices were archived before
replacement. All twelve protected Lissa files retain their original SHA-256 hashes.
Lissa's reference, model settings, expression assets and running service were not
modified or restarted. No reference audio was made public.

The selector offers Lissa, Emma and Olivia and hides Jenifer. Emma and Olivia
have now been registered ACTIVE and shared in the configured database, with private
verified reference paths; the entire existing Lissa registry row was compared and
remained unchanged.

The already-running Lissa engine did not have these new IDs in memory. Rather than
restart it, `deployment/clone_voice_api.py` runs an independent CUDA CosyVoice
instance on localhost port 8780 for Emma and Olivia. Lissa remains on port 8767.
The app merges both catalogs and routes only the new IDs to 8780. The real app
catalog was checked against both running services and the configured database:
all three voices are visible, Lissa remains the default, and serviceReady is true.
Test Agent, admin Create/Edit Agent, BPO Create/Edit Agent and the BPO voice library
use this shared catalog; local clones are not shown as missing provider profiles.

Start the independent service with `bash deployment/Start-CloneVoices.sh` from the
project checkout. This launch is separate from Lissa and must be included wherever
the local AI services are started after a machine reboot. No Lissa service restart,
model reload or cache modification was performed. The live service requires CUDA and refuses a slow CPU fallback. Both new voice
caches and GPU kernels are warmed before readiness; their model weights, float32
precision and reference recordings are retained.

If voice engines are offline, approved registry voices remain available for agent
configuration, while live preview/testing is marked unavailable. Stored ownership,
global access, approval and transcript/rights checks still apply.

## Live speed correction

The initial CPU-only live service caused severe response delay and chunk starvation.
It was replaced with CUDA inference on the available RTX 3090, restarting only
Emma/Olivia's port 8780 service. DeepSpeed's unused training integration is disabled
only within that process to avoid requiring a CUDA compiler for inference.

Four direct TTS stream measurements gave first audio in 0.758–0.921 seconds,
real-time factors of 0.397–0.496, and no simulated underruns with a 200 ms initial
buffer. These are direct synthesis measurements, not end-to-end STT/LLM call timing.
Results and generated WAVs: `.data/clone-response-review/`. Lissa remained ready
with an unchanged speaker cache. No speech speed-up or reference pitch change was
used to obtain the improvement.

The final restarted service reports device=cuda and cached IDs emma/olivia, matching
the app warmup contract. A follow-up benchmark uses the worklet’s actual 60 ms
startup buffer (`final-60ms-results.json`).
